# Checkpoint — 存档工作进展

## 触发场景

- 完成了一个阶段性任务（如某个需求的某个子任务完成）
- 即将切换到另一个任务或需求
- 当前对话较长，担心上下文丢失
- 做出了重要的技术决策
- 一天工作结束时

## 执行步骤

### 第 1 步：收集当前状态

在执行 checkpoint 之前，先收集以下信息：

1. **本次对话做了什么**：回顾当前对话中完成的工作、做出的决策、遇到的问题
2. **当前在做什么**：正在进行中的任务和状态
3. **下一步计划**：接下来要做什么
4. **卡点**：是否有未解决的问题或待决策事项

### 第 2 步：写入工作日志

将记录**追加**写入 `docs-harness/memory/YYYY-MM-DD.md`（使用当天日期）。

如果文件不存在，创建并写入以下格式：

```markdown
# 工作日志 YYYY-MM-DD

## HH:mm — [简要标题]

### 完成事项

- 具体完成的工作内容
- 关键代码变更摘要（文件名 + 改动概述）

### 决策记录

- 做了什么决策，为什么这么决策

### 进行中

- 正在做的事情，当前进度

### 遇到的问题

- 遇到了什么问题，如何解决的（或尚未解决）
```

如果文件已存在，在末尾追加新的时间段记录（`## HH:mm — [简要标题]`），不覆盖已有内容。

### 第 3 步：更新 progress.md

**覆盖写入** `docs-harness/progress.md`，反映最新的项目状态：

```markdown
# 项目进展快照

> 最后更新: YYYY-MM-DD HH:mm

## 当前进行中

- [ ] 需求/任务名称 — 当前阶段描述

## 待办

- [ ] 待开始的工作

## 已完成（最近）

- [x] 最近完成的工作（保留最近 5-10 项）

## 卡点 / 待决策

- 需要讨论或决策的事项

## 近期决策记录

| 日期       | 决策     | 原因     |
| ---------- | -------- | -------- |
| YYYY-MM-DD | 决策内容 | 决策原因 |
```

### 第 4 步：更新需求任务进度（如适用）

如果本次工作涉及某个具体需求，同步更新对应的 `docs-harness/requirements/NNN-*/task-items.md` 中的任务状态。

### 第 5 步：补充功能文档（如适用）

如果本次工作新增了用户可见的功能（新页面、新 API、新监控面板等），在 `docs-harness/features/` 中创建功能文档，并更新 `docs-harness/features/README.md` 索引。功能文档应包含：功能概述、数据流图、API 说明、配置项、注意事项。

### 第 6 步：更新架构文档（如适用）

如果本次工作涉及架构变更（新 API 端点、新中间件依赖、新的跨服务调用），检查 `docs-harness/architecture/` 中相关文档是否需要更新（如 report.md 的 API 端点表）。

## 注意事项

- 工作日志是追加式的，同一天可以多次 checkpoint
- progress.md 是快照式的，每次覆盖写入最新状态
- 记录要具体，避免泛泛而谈（如「改了一些代码」），应写明具体改了什么文件、为什么改
- 决策记录要包含「为什么」，而不只是「是什么」
