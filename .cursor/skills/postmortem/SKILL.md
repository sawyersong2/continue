# Postmortem — 事后复盘

## 触发场景

- 修复了一个难以排查的 bug
- 线上出现故障并已修复
- 开发过程中踩了一个大坑，耽误了较多时间
- 做了一个后来证明是错误的技术决策并已纠正
- 用户说「复盘一下」「总结一下教训」等

## 执行步骤

### 第 1 步：还原事件时间线

与用户一起还原以下信息（如果用户没有提供，主动询问）：

1. **问题是什么**：出了什么问题，现象是什么
2. **如何发现的**：谁/什么时候/怎么发现的
3. **排查过程**：试了哪些方案，走了哪些弯路
4. **最终解决**：怎么解决的，改了什么

### 第 2 步：分析根因

区分两个层次：

- **表面原因**（直接原因）：代码层面是什么导致了问题
- **深层原因**（根本原因）：为什么会写出这样的代码？是架构设计不合理？是缺少文档？是测试覆盖不足？是对某个组件理解有误？

### 第 3 步：制定改进措施

列出具体可执行的 action items，按优先级排序：

- 代码层面：需要补充哪些测试、需要重构哪些代码
- 文档层面：需要更新哪些文档、需要补充哪些注释
- 流程层面：需要调整哪些开发/部署流程
- 规范层面：需要新增哪些编码规范

### 第 4 步：写入复盘记录

创建 `docs-harness/postmortem/YYYY-MM-DD-简短标题.md`，格式：

```markdown
# [简短标题]

> 日期: YYYY-MM-DD
> 影响范围: [模块/服务名]
> 严重程度: [高/中/低]

## 事件概述

一句话描述发生了什么。

## 时间线

| 时间 | 事件               |
| ---- | ------------------ |
| ...  | 发现问题           |
| ...  | 开始排查           |
| ...  | 尝试方案 A（失败） |
| ...  | 找到根因           |
| ...  | 修复上线           |

## 根因分析

### 表面原因

...

### 深层原因

...

## 改进措施

- [ ] Action item 1
- [ ] Action item 2

## 经验总结

这次踩坑的核心教训是什么，一句话概括。
```

### 第 5 步：更新索引

在 `docs-harness/postmortem/README.md` 的复盘列表表格中添加本次记录。

### 第 6 步：判断是否需要更新规则

评估本次经验教训是否需要沉淀到更持久的位置：

- **更新 `.cursor/rules/`**：如果教训涉及编码规范或通用最佳实践
- **更新架构文档**：如果教训涉及架构设计缺陷
- **更新 Skill**：如果教训涉及某个特定模块的知识（如调度模块）

如果需要更新，在复盘记录中标注，并征求用户意见后执行。

## 注意事项

- 复盘的目的是学习，不是追责，保持客观和建设性的语气
- 重点是「下次怎么避免」，而不是「谁的错」
- 改进措施要具体可执行，避免泛泛而谈（如「以后多注意」）
- 如果根因是重复出现的模式，特别值得写入 Rules
