# New Requirement — 新建需求文档

## 触发场景

- 开始一个新需求或优化任务
- 用户说「新建需求」「创建需求文档」「开始做 XXX」等
- 需要对一个改动进行正式的需求分析和方案设计

## 执行步骤

### 第 1 步：确定需求信息

与用户确认以下信息（如果用户已提供则直接使用）：

1. **需求名称**：简短的英文标识，使用 kebab-case（如 `cleanup-user-instance`）
2. **需求简述**：一句话描述需求目标

### 第 2 步：分配编号

读取 `docs-harness/requirements/README.md`，找到当前最大编号，分配下一个三位数编号。

如果索引为空，从 `001` 开始。

### 第 3 步：创建需求目录和文件

创建 `docs-harness/requirements/NNN-name/` 目录，生成三个模板文件：

#### requirements.md

```markdown
# [需求名称]

> 编号: NNN
> 状态: 规划中
> 创建日期: YYYY-MM-DD
> TAPD Story ID: （创建 TAPD 需求单后填写 19 位 ID）

## 1. 概述

### 背景

[为什么要做这个需求]

### 目标

[这个需求要达成什么目标]

### 范围

[需求涉及哪些模块/服务]

## 2. 现状分析

[当前系统在这个方面是怎么工作的，有什么问题]

## 3. 需求详述

[具体要做什么，功能/非功能需求]

## 4. 技术方案

> 详细方案见 [solution.md](solution.md)

[简要说明技术方向]

## 5. 影响范围

[会影响哪些模块、接口、数据库、配置]

## 6. 风险评估

[可能的风险和应对措施]

## 7. 验收标准

- [ ] 验收条件 1
- [ ] 验收条件 2

## 8. 排期

> 详细任务拆解见 [task-items.md](task-items.md)

[预估工作量和里程碑]

## 9. 附录

[参考资料、相关链接]
```

#### solution.md

```markdown
# [需求名称] — 实现方案

> 需求编号: NNN
> 最后更新: YYYY-MM-DD

## 方案概述

[整体技术方案概述]

## 方案对比（如有多方案）

| 维度   | 方案 A | 方案 B |
| ------ | ------ | ------ |
| 描述   | ...    | ...    |
| 优点   | ...    | ...    |
| 缺点   | ...    | ...    |
| 工作量 | ...    | ...    |

**选定方案**：[方案 X]，原因：[...]

## 架构设计

[架构图、流程图（使用 Mermaid）]

## 核心代码变更

[列出需要改动的文件和改动概述]

| 文件 | 改动类型 | 说明 |
| ---- | -------- | ---- |

## 数据库 / 中间件变更

[如涉及数据库表变更、Redis 结构变更、Kafka Topic 变更等]

## 兼容性考虑

[向前/向后兼容性，灰度策略]
```

#### task-items.md

```markdown
# [需求名称] — 任务拆解

> 需求编号: NNN
> 最后更新: YYYY-MM-DD

## 任务列表

| #   | 任务       | 状态   | 说明 |
| --- | ---------- | ------ | ---- |
| 1   | [任务描述] | 待开始 | ...  |

## 状态说明

- **待开始** — 尚未开始
- **进行中** — 正在开发
- **已完成** — 开发并测试完成
- **已取消** — 不再需要

## 进度记录

### YYYY-MM-DD

- 初始化任务列表
```

### 第 4 步：TAPD（BKW）需求单

在本地三件套文件已创建后，按 **`.cursor/rules/tapd-requirement-sync.mdc`**（或 `.claude/rules/tapd-requirement-sync.mdc`）执行：

1. 使用 **TAPD MCP** 调用 `stories_create`，`workspace_id` 为 **69990282**，需求标题 **`【云桌面后台】` + 与本文档一致的需求简称**。
2. 将返回的 **19 位 Story 长 ID** 填入本需求 `requirements.md` 顶部的 `TAPD Story ID` 行。
3. 若 MCP 不可用，在 `docs-harness/progress.md` 记「待补 TAPD」，不阻塞后续步骤。

后续本地状态从「规划中 → 开发中 → 测试中 → 已完成/已取消」变化时，在同一规则下用 `stories_update` 同步 TAPD（优先传 `status` 内部码，如 `status_3` / `status_4` / `status_8` / `status_9`）。

### 第 5 步：更新需求索引

在 `docs-harness/requirements/README.md` 的需求列表表格中添加新记录：

```markdown
| NNN | [name](NNN-name/) | 规划中 | YYYY-MM-DD | 需求简述 |
```

### 第 6 步：更新 progress.md

在 `docs-harness/progress.md` 的「当前进行中」或「待办」部分添加新需求。

## 注意事项

- 模板中的占位内容（如 `[为什么要做这个需求]`）应由用户填写或由 AI 根据用户描述生成
- 如果用户已经提供了足够的需求信息，可以直接填充模板而非留空
- 编号必须是三位数，保持连续
- 创建完成后提示用户接下来可以开始填写需求详情或直接讨论方案
